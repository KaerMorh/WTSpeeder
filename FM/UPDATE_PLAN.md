# WTSpeeder 应用与 FM 更新实施方案

状态：需求与交接方案，尚未实现。由后续执行任务完成开发、验证、Public 发布和首次自动 FM 初始化。

## 1. 目标与范围

1. GitHub 自动从 War Thunder Datamine 更新公开 FM 数据，检查周期为 6 小时。
2. 客户端提供应用更新按钮，用于功能迭代和程序修复。
3. FM 独立于应用发版；同一更新页面提供 FM 检查、下载、选择和备注查看。
4. 客户端保留最近两个 FM 版本和当前人工稳定版，支持自由切换，只推荐最新版本。
5. Private 保持本地构建；上传、推送和云端构建仅涉及 Public 内容及公开数据。
6. 不要求另开仓库、部署服务器或启动后台常驻服务。

## 2. 当前代码事实与注意事项

- FM/update_fm.py 已提供下载、解析、CSV 保存和交互式差异确认，需要扩展非交互运行能力，而非重写一套解析器。
- 上游当前配置为 gszabi99/War-Thunder-Datamine 的 master 分支；开始执行时检查其可访问性和路径。
- 数据为 FM/fm_data_db.csv 和 FM/fm_names_db.csv，两者必须属于同一快照。
- FM/fm_version 目前未形成完整版本管理逻辑，不能未经核实就把其中数值作为应用版本或新 FM 版本。
- core/fm_db.py 使用 resource_path 加载随程序打包的 CSV；目前没有远程更新或版本选择。
- public.spec / private.spec 当前都收集整个 FM 目录。改为精确打包运行必需的数据和清单，避免打包历史备份、维护脚本及方案文档。
- 应用设置存储在 APPDATA/WTFriendCounter 下。沿用已有位置，不顺带改名或迁移全部配置。
- 当前无检出的 .github/workflows，无已实现的应用升级流程。
- FM/update_fm.py 已有用户未提交改动，执行前必须阅读并保留。
- .gitignore 为默认忽略、精确放行模式。新增工作流需要最小白名单调整，禁止整体放开隐藏目录或构建目录。

## 3. FM 版本模型

每个不可变 FM 版本包括两份 CSV 和一个简单 JSON 清单。无需引入数据库。

必要字段：

- id：唯一 FM 版本标识，独立于应用版本。
- published_at：真实发布时间，UTC ISO 8601；UI 转换为用户本地时间。
- kind：manual 或 automatic，显示为“人工构建”或“自动构建”。
- notes：非空中文更新说明。
- schema_version：CSV 格式版本，客户端只启用自己支持的版本。
- source_commit：自动构建的上游固定提交 SHA；初始人工版无法确认来源时填空并注明本地基线，禁止猜测。
- files：两份 CSV 的固定地址、SHA-256 和必要大小信息。

一个轻量远端索引记录已发布版本元数据和 stable_id。latest 按实际发布时间和确定的并列排序规则计算，禁止按文件修改时间或类型计算。

人工稳定版是由 stable_id 指向的版本，不能被定时任务改写。以后可通过同一个维护脚本的明确人工发布入口更新 stable_id；不需要另做管理网站。

自动说明应来自实际差异，例如“新增 3 个机型；修正 2 个机型速度限制；更新 4 条名称映射”，详情可列出涉及机型。不要使用模型生成说明，不要编造游戏版本名，也不要只写“自动更新”。

## 4. 首次人工基线与初始化顺序

1. 在任何上游更新前，原样冻结当前两份 CSV，校验哈希并形成首个人工稳定版。
2. 此版本备注严格为“问鼎九天版本FM”。发布日期填写实际建立该版本的时间；不要推断它等于游戏更新日期。
3. 将此基线作为应用内置离线兜底数据，完成更新功能开发与 Public 构建。
4. 发布公开基线数据和 Public 应用；Private 如需构建，仅留本地。
5. 在 GitHub 手动触发首次自动 FM 构建，从固定上游提交生成第一个自动版本。
6. 唯一初始化例外：首次自动构建即使与人工基线数据相同，也建立初始自动版本，备注明确“首次自动构建，与人工稳定版数据一致”。只有校验成功时才允许发布；失败不能以空版本充数。该例外只适用于从未存在自动版本的初始化，重复运行不得继续增版。
7. 此后启用每 6 小时的检查，严格遵守无变化不发版。

第 6 条用于同时满足“先人工基线，再构建一个自动版本”和后续去重要求；不意味着每次手动触发都强制发版。

## 5. GitHub 自动更新流程

- 一个 FM 工作流支持 schedule（每 6 小时，避开整点）和 workflow_dispatch；不把检查周期做成客户端常驻任务。
- 使用并发限制避免两个 FM 发布同时修改索引；不使用会中断发布到一半的策略。
- 先读取上游分支 HEAD，与最近一次成功检查的提交比较。相同则结束，不生成版本、备注或 Release。
- HEAD 变化后，固定到该提交读取所有文件，禁止同一版本混用不同时间的 master 数据。
- 如相关 FM 子树未变化，可提前结束；否则生成候选 CSV 并与最新已发布自动数据比较（首次以人工基线为参照）。
- 使用稳定排序、统一序列化以及既有数值比较规则判断有效数据变化。字段与名称映射任一变化均计入；时间戳、换行或排列顺序变化不算新版本。
- 上游 HEAD 变化但数据相同：只记录检查状态，不更新 FM 版本和发布日期。检查状态必须独立于数据版本元数据；可以使用一份小型状态文件，无需额外服务。
- 检查状态只有在成功完成该提交检查后更新；下载失败、限流、解析失败不得标为成功或“无更新”。
- 不允许因单文件下载失败而发布部分更新。校验 CSV 表头、非空数据、关键数值合法性、唯一键和新增/变更名称映射关系；兼容已有基线的已知缺失，不能机械删除全部历史记录。
- 明确处理上游已有名称映射的变化，不能只添加缺失名称。未见于上游的旧条目不自动大批删除，删除策略本次不扩展。
- 有有效变化时生成备注、哈希和不可变版本文件，更新仓库当前 CSV 与公开索引。
- 建议直接使用同一公开仓库的版本目录和单次提交发布两份 CSV、清单、索引；客户端按该发布提交读取文件，保证一致性。FM 不需要独立 Release，更不要混入应用 latest Release。
- 仓库仅增长新版本时产生发布提交；检查状态变化可单独记录但不视为发版。不要创建无变化的应用 Release。
- GitHub 定时任务可能延迟；“每 6 小时”是计划检查周期，不承诺实时到点。

## 6. 客户端保存、选择与推荐

本地结构使用现有用户数据目录下的 fm/versions/<id>/，另存简单状态 JSON 记录 selected_id 和已同步索引。禁止把更新写入 PyInstaller 临时解压目录。

保留集合：

1. 已同步的、客户端兼容的最近两个已发布 FM 版本（人工和自动混合排序）。
2. GitHub 当前 stable_id 对应的人工稳定版。
3. 用户当前选择的版本若不在前两项中，额外保留，直到用户切换离开。

按 id 去重：通常 2～3 份，用户固定旧版时可临时超过 3 份。两份 CSV 始终一起保留或删除。“最近两个”不是“当前版本加两个历史版本”。内置基线作为额外离线兜底，不参与可写缓存清理。

- 新安装首次使用内置人工基线；同步成功后无既有选择的用户默认选择最新兼容版本。
- 用户手动选择后持久化选择；后续同步只下载、刷新推荐状态，不强制切换。
- 推荐标记只给按发布时间最新的版本，不因稳定身份给第二个推荐标记。更新的人工版也可以成为唯一推荐。
- 如远端最新版本格式不兼容，显示“需升级应用”，禁止加载，也不能把更旧版本谎称“最新”；旧版本保持可用。
- 本地离线时显示“本地最新 / 上次检查时间”，不声称已经确认远端最新。
- 更新人工稳定版指针时下载并验证新稳定版；旧稳定版仅在不属于最近两版、也未被选中时清理。
- 下载到临时目录，核验两份文件、元数据和解析结果后切换为完整版本目录。更新失败保留旧选择、旧文件和旧索引。
- 仅清理明确属于版本缓存的完整目录；不得删除未知文件、用户配置或正在使用的数据。
- 第一版切换在下次启动生效，UI 明确区分“当前使用”和“下次启动使用”；重启前两者均不可清理。不做运行中共享 FM_DB 热替换。

## 7. 用户界面

在现有 Tkinter 设置窗口增加一个“更新”页，不替换 UI 框架。

- 应用区域：当前版本、可用版本、更新说明、“检查应用更新”“下载并安装”。
- FM 区域：当前使用版本、下次启动版本、同步时间、“检查并下载 FM 更新”、版本选择与详情。
- 每个 FM 版本可见版本号、更新日期、更新说明、来源类型，以及适用的“推荐”“人工稳定版”“当前使用”标签。
- 选择条目必须能看见完整说明，不只把说明留在远端 JSON；长说明可以显示在旁边详情框。
- 网络操作在现有线程模式下后台执行，UI 更新通过 root.after；避免重复点击产生并发下载。
- 清楚显示检查中、无更新、下载成功、失败可重试、格式不兼容。断网不影响主功能启动。
- 本次不增加自动静默安装、通知中心、定时后台进程或复杂下载任务系统。

## 8. 应用版本更新与发布

- 单一明确的应用版本常量，采用可正确比较的版本格式。初始值结合实际公开 Release/标签核实，禁止套用 fm_version。
- GitHub 应用发布工作流只构建 public.spec；通过明确应用 tag 或手动发布触发，FM 检查不触发应用构建。
- Release 仅上传精确指定的 Public EXE 和校验清单，附用户可见功能更新说明。
- Public 客户端下载与校验后，在用户启动安装操作时退出，由最简单的本地 Windows 脚本等待当前进程结束、保留旧 EXE、替换并重启。只在路径可写时执行；权限不足或替换失败时保留旧程序并提供已下载文件与手动替换说明。
- 更新辅助脚本避免拼接不可信 shell 参数；验证带空格和中文路径。不要引入独立更新服务、嵌入式运行时、自制安装器框架。
- 保留现有配置、FM 缓存和用户选择。
- 源码运行模式不自行替换文件；提示使用源码更新方式。
- Private 界面明确显示“本地构建，应用更新不适用”，禁用 Public 应用覆盖逻辑；FM 更新仍可使用。
- 本地双版本构建能力可保留，但云端工作流不得调用会构建 Private 的整套脚本。
- 推送前检查目标 public 远端、提交历史和文件内容，禁止将含私有文件的历史推向公开仓库；必要时从干净公开分支应用公开改动，不重写或删除用户私有历史。

## 9. 实施顺序与不过度工程化约束

按以下顺序逐步交付，不先建通用基础框架：

1. 检查已有改动，冻结人工基线和备注。
2. 扩展现有 FM 脚本：非交互、固定提交、差异判定、说明和失败处理。
3. 实现小型 FM 清单、缓存与选择逻辑，接入 FM_DB 的路径选择。
4. 增加现有设置页和 FM 同步按钮。
5. 增加最小 Public 应用更新与发布流程。
6. 完成针对性验证，再发布 Public，最后 GitHub 首次自动 FM 构建与定时检查。

约束：复用当前 Python/Tkinter/PyInstaller；客户端 JSON、哈希、文件管理优先标准库，维护脚本复用现有 requests。以少量明确函数/模块实现，不引入 ORM、依赖注入、事件总线、策略层、插件架构、通用多渠道升级系统、增量补丁或专用服务。避免无关重构；不要为了测试建立新的庞大基础设施。

## 10. 验收清单

- 当前人工基线两份 CSV 内容与实施前一致，备注精确为“问鼎九天版本FM”。
- 首次 GitHub 自动构建成功，稳定版不被覆盖；初始化重复运行不会重复造版本。
- 上游提交不变：无新版本；提交变但数据不变：无新版本；数据或名称映射变：恰好一个新版本且说明准确。
- 下载失败、解析失败、哈希不符：不发布半成品、不切换用户数据、不清理旧版本。
- 最近两版与人工稳定版正常保留，重复项去重；固定旧版及重启前正在使用版不被误删。
- 人工版更新且发布时间最新时，只推荐人工版；自动版更新后，只推荐自动版。
- 选择持久化，下次启动加载所选整套 CSV；断网、首次启动、损坏缓存均能继续使用有效数据或内置兜底，并显示实际使用版本。
- 每个版本在 UI 中有可读日期和完整备注；不兼容版本不可启用。
- Public 应用能完成版本检查、下载校验与退出后替换；失败保留旧程序，用户设置与 FM 选择不丢失。
- Private 本地构建仍可用，禁止安装 Public 替换；远端提交及资产中没有 Private 文件或私人代码。
- 测试重点为上述状态转换与故障恢复；用小型离线 fixtures 验证逻辑，加一次 Public 打包运行检查和实际 GitHub 首次工作流验证，不进行无意义的重复全量测试。

## 11. 给后续执行模型的交接提示

请先阅读根目录 AGENTS.md 和本方案，按本方案完成实现与验证。保持实现简单，保留已有未提交改动，不扩展需求。Private 只在本地，公开操作明确指向 public 远端。先保存当前人工稳定版，再发布 Public，最后在 GitHub 构建首个自动 FM 版本并启用 6 小时检查。遇到认证或远端权限阻碍时，完成所有不受影响的本地工作，并准确说明尚未完成的发布步骤；不得声称未运行的工作流已经成功。
